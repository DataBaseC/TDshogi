Security & Engineering Review

TDShogi 在线将棋平台 · 代码审查报告

对 v1.4.4（commit 29ca712）完成全量代码通读，并在隔离实例上对关键链路做了动态复现验证： 注册/登录/对局/结算/导出/观战/重启恢复均实测跑通；同时确认了 4 类严重问题（可导致服务崩溃、 账号接管、数据窃取与越权读写）。总体评价：工程结构与注释质量高于同类项目平均线， 但“身份 = id”的凭证模型在多处实现漏口，安全加固需要一个集中修复版本。

审查范围 23,000+ 行（server + src 26 模块 + public 前端） 复现环境 Node v22.23.1 · Linux · 隔离 DATA_DIR

00结论摘要

项目主体（服务端权威规则、对局状态机、棋谱存取、赛事、限流、审计、备份）实现扎实， 大量设计取舍写在注释里且有据可查。但本轮审查确认了 4 个 P0（严重）与 5 个 P1（重要）问题——其中两个 P0 恰好都指向同一个系统性弱点： “玩家 id（含正式账号 id）在多处公开可见，却被当作可信任凭证使用”； 另有一个未捕获异常可在单条 WebSocket 消息内打崩整个进程。

所有 P0 问题都已在本地隔离实例上实际复现（含完整攻击链），修复成本均不高， 建议合并为一个 v1.4.5 安全修复版本优先发布。

01项目速览

TDShogi 是一个单进程（Node + Express + ws + better-sqlite3）的在线将棋对战平台： 游客免注册开局、服务端权威规则判定、实时观战、感想战、棋谱 KIF/CSA 导出、 ELO + 等级系统、单败淘汰/瑞士制赛事、管理后台、多语言（中/英/日）。

结构上服务端拆为 26 个模块（src/rooms/ 下按 mixin 拆分状态机），前端为无构建的 24 个脚本；数据全部落在单个 SQLite 库。审查发现该上传仓库是「部署同步产物」， 不含 tests/、scripts/、docs/（README 引用的 e2e、i18n 报告、 pack 脚本均不在此仓库内）——本轮审查以仓库内实际可见代码为准。

技术栈：Node ≥ 22 · express 4.22 · ws 8.21 · shogi.js 5.5 · better-sqlite3 13.0

运行时验证：npm install 成功（151 包）；服务启动正常；完整对局→认输→ ELO 结算（1516 / 1484）→ KIF/CSA 导出→重启快照恢复，均实测通过。

02审查与验证方法

静态通读覆盖：服务端 26 模块全文 + 前端关键渲染路径；动态验证在隔离实例（独立 DATA_DIR + 端口）上进行，包含：

  • WS 对局全流程冒烟（建房/加入/座位探测/手番校验/非法走法拒/走子推进/观战/认输结算/导出/鉴权/限流）：终版脚本 18/18 通过；初版脚本曾报 3 项失败，经复测确认均为脚本自身消息残留误报，非服务端缺陷（过程记录见附录脚本注释）；
  • 棋谱导出（KIF/CSA 格式与内容）、复盘数据权限探针、路径穿越探针；
  • 注册/登录/弱密码/重名/限流（auth 20 次/5 分钟、WS 40 条/秒、admin 登录 8 次/10 分钟）；
  • 重启恢复：杀进程 → 重启 → 「已恢复 1 场未完成对局」，重连后走法完整；
  • 安全头（CSP / nosniff / X-Frame-Options / X-Request-Id）与缓存策略实测；
  • 攻击面复现：对 P0/P1 每一项构造最小复现（详见附录与 repro/ 脚本）。

局限：未做移动端真机、多浏览器矩阵、长期压测与内存泄漏观测；未审计 shogi.js / better-sqlite3 三方库内部实现。

03P0 · 严重问题

P0-1单个 WebSocket 消息即可打崩整个服务进程

位置
src/accounts.js:127（verifyToken）· src/admin.js:67（同款）· server.js:116（Host 解析）
等级
P0 · 远程拒绝服务（无需任何账号）
状态
已复现：进程以未捕获异常退出

verifyToken 在做常量时间比较前用 UTF-16 字符长度（sig.length） 做前置校验，但 Buffer.from(sig) 得到的是 UTF-8 字节串。 当签名段使用多字节字符（如 32 个 emoji = 64 个字符、128 字节）时，长度检查通过、 crypto.timingSafeEqual 因字节长度不等抛 RangeError； 该异常发生在 handleConnection（WS 握手回调）中且无任何 try/catch → 整个 Node 进程崩溃，全部在线对局断开。 

// 攻击者视角（单行，任何人均可执行）
node -e 'const WS=require("ws");
new WS("ws://target/ws?guest=" + encodeURIComponent("aa.123." + "😀".repeat(32)));'

// 服务端观察到的崩溃：
// RangeError: Input buffers must have the same byte length
//   code: 'ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH'
//     at Object.verifyToken (src/accounts.js:127:49)
//     at Protocol.handleConnection (src/protocol.js:68:32)
//     at WebSocketServer.<anonymous> (server.js:119:12)
// → 进程退出，HTTP/WS 全断

第二个同族向量：server.js:116 的 new URL(req.url, 'http://' + req.headers.host)。 攻击者发送畸形 Host 头（如 a b）时 new URL 抛 ERR_INVALID_URL，同样未捕获 → 进程崩溃（已复现）。

修复建议

// ① 字节级校验 + 字符白名单 + 兜底（accounts.js / admin.js 同改）
function verifyToken(token) {
  ...
  const expected = crypto.createHmac('sha256', SESSION_SECRET)
    .update(`${accountId}.${ts}`).digest('hex');
  // 必须是 64 位小写 hex，才允许进入比较；Hex 字符集下 length === byteLength
  if (typeof sig !== 'string' || !/^[0-9a-f]{64}$/.test(sig) || sig.length !== expected.length) {
    return null;
  }
  return crypto.timingSafeEqual(Buffer.from(sig, 'hex'), Buffer.from(expected, 'hex'))
    ? accountId : null;
}

// ② 连接边界加一次性保险（server.js）：任何握手异常都只拒绝该连接
wss.on('connection', (ws, req) => {
  try {
    const url = new URL(req.url, 'http://localhost');   // 不信任 Host，消灭向量二
    ...
    protocol.handleConnection(ws, guestId, netInfo.clientInfo(req));
  } catch (err) {
    log.error('ws', '握手异常，拒绝该连接', { err });
    try { ws.close(); } catch (_) {}
  }
});

修复验收：加入「畸形 token / 畸形 Host 不允许崩进程」回归用例（附录脚本 07/08 可直接转正为测试）。

P0-2默认签名密钥内置源码 → 任意账号可被伪造接管

位置
src/accounts.js:25 — process.env.SESSION_SECRET || 'tdshogi_session_secret_change_me'
等级
P0 · 账号接管（跨账号越权）
状态
已复现：伪造令牌被服务端接受，可读私密资料、连 WS 顶替身份

未配置 SESSION_SECRET 时使用源码内置常量签名。该源码是公开仓库， 且账号 id 本身是公开数据——大厅对局列表（playerIds）、个人页棋谱列表、 悬停卡、管理接口等处均可见。攻击者拿到任一账号 id 后，只需用内置密钥离线伪造 <accountId>.<ts>.<hmac> 三段令牌，即可：

公开接口拿到 accountId→ 用内置密钥计算 HMAC→ 伪造令牌通过验证→ 读私密资料 / 顶替对局 / 检索棋谱

实测：伪造令牌连 WS → hello.playerId = 受害者 id；/api/account/profile 返回其私密字段。

修复建议

// 首启生成随机密钥并持久化（零运维负担），同时在检测到配置缺失时警告
function resolveSessionSecret() {
  if (process.env.SESSION_SECRET) return process.env.SESSION_SECRET;
  const f = path.join(DATA_DIR, 'secret.json');
  let s = readJson(f, null);
  if (!s || !s.key) {
    s = { key: crypto.randomBytes(32).toString('hex'), createdAt: Date.now() };
    writeJson(f, s);                         // 目录权限 600
    log.warn('security', '已自动生成随机会话密钥（建议显式配置 SESSION_SECRET）');
  }
  return s.key;
}
// 启动自检：使用默认/弱密钥 → 高亮警告；提供 REQUIRE_STRONG_SECRETS=1 强制失败

注意迁移期：密钥更换会使旧令牌全部失效（用户需重新登录），发版说明中应注明。

P0-3注册时 guestId 不验证来源 → 可窃取任意注册用户的全部数据

位置
src/accounts.js:60-88（register → migrateGuestData，无所有权校验）
等级
P0 · 数据窃取（战绩 / 棋谱 / ELO / 会话）
状态
已复现：受害者 1516 分 1 局记录全部被迁移到攻击者新账号

POST /api/register 接受任意 guestId 并把「该 id 名下的评级、棋谱、 会话文件」迁移到新账号——但没有任何机制证明注册者真的持有该身份。 由于账号 id 与游客 id 在公开页面可见，攻击者用受害者 id 注册就能干净地拿走： 该账号的全部棋谱、ELO 战绩、会话（名字/头像）——而受害者账号随即变回 1500 分空号。 实测复现输出： 

V 战绩（被盗前）:  rating=1516  games=1  records=1
攻击者注册 guestId=<V 的 accountId> → 注册成功
攻击者账号战绩:      rating=1516  games=1  records=1   ← 全部到手
V 账号战绩（盗后）:  rating=1500  games=0  records=0

修复建议

最小修复（立刻可上）：拒绝将已注册账号的 id 作为迁移来源；同时对迁移写审计日志：

function register(username, password, guestId = null) {
  ...
  if (guestId) {
    if (accounts[guestId]) {                    // 目标 id 已是注册账号 → 绝不迁移
      log.warn('accounts', '拒绝迁移：目标 id 已是注册账号', { guestId });
    } else {
      migrateGuestData(guestId, id);
    }
  }
}

完整修复（推荐）：迁移权 = 游客凭据。游客会话文件（sessions/<id>.json）里生成 一个不下发的 migrationKey；客户端从自己浏览器携带该 key 才能迁移。 这样即使 id 泄漏，也无法被第三方抢注。

位置
src/http/routes/records.js（export / playback / review / comment / bookmark / variation）· src/http/context.js resolvePlayer
等级
P0 · 越权读写（隐私 + 内容完整性）
状态
已复现：伪造评论已落盘，作者字段为受害者

resolvePlayer() 对“不带点”的输入原样返回；六个棋谱接口随后把它当作 playerId 做 isOwner 判定。于是任何人只要知道受害者的 公开 id（正式账号 id / 游客 id 均公开），不带任何令牌即可： 导出/回放/完整复盘其私有棋谱；以受害者名义写入评论、书签、变着。 README 声称的「只能复盘自己的棋谱」在这些接口上并不成立（此前 §Q7 修复的只是 /api/history 与 /api/records/search 两条路径，同类问题在兄弟接口仍在）。 

# 无任何 token，仅凭公开 id：
GET  /api/records/<id>/export?guest=<victimId>      → 200  （KIF 全文到手）
GET  /api/records/<id>/review?guest=<victimId>      → 200  （含评论/书签全量）
POST /api/records/<id>/comment  {guest:<victimId>,...}
     → 200 {"ok":true, comments 落盘 authorName=受害者}
POST /api/records/<id>/bookmark {guest:<victimId>,...} → 200 （书签被改）

修复建议

把「账号身份必须凭签名令牌」收进唯一入口，原始 id 只对游客生效（游客 id 即凭证的 现状可暂保留，但建议下一版引入游客会话撤销机制）：

// context.js：统一身份解析——遇到“考据为已注册账号的裸 id”时必须凭令牌
function resolvePlayer(raw) {
  if (!raw) return null;
  if (String(raw).includes('.')) return accounts.verifyToken(raw) || null;
  // 裸 24-hex：若是注册账号的 id，则裸值不可信（账号必须用令牌）
  if (/^[0-9a-f]{24}$/.test(raw) && accounts.getAccount(raw)) return null;
  return raw; // 游客 id（现状）：id 即凭证
}
// 写操作（comment/bookmark/variation）同改，并补 e2e：伪 guest 参数必须 403

04P1 · 重要问题

P1-1重复操作静默判负：双击「加入/匹配」直接输棋

位置
src/rooms/lifecycle.js:141 / 197 / 214（joinRoom / quickMatch 先 _autoResignAndLeave 后校验）
状态
已复现三个变体：重复 join_room、双击 quick_match、输错房间码 → 当前对局均被判负（「投了」）

玩家对局中若重复发送加入/匹配类消息（双击按钮、页面重放、输错码重试）， 控制流会先执行「自动认输退出对局」，再去校验新目标——结果：一次手滑 = 直接输棋， 且对局聊天区没有留下任何能解释原因的痕迹。实测：双击 quick_match 后对手立即收到 game_over detail=投了。

修复建议

  • 服务端调整顺序：先校验目标合法性（房间码存在、非自身、非同一房间），再做切换处理； 「已在该房间/重复请求」应返回 no-op 错误而不是触发认输路径。
  • 对同类操作做幂等窗口（例如 2 秒内的重复 join/quick_match 直接忽略）。
  • 前端：提交后禁用按钮直至收到响应（双保险）。
  • 若产品上确实要保留「换玩法自动认输」（PLAN §H 的设计），至少要求显式确认参数 （confirmLeave: true），并要求前端先弹确认框。

位置
public/js/util.js:30（esc 只转 & < > "）· public/js/admin.js:275-276、359-365（用户名嵌入单引号 onclick）

P1-4后台隐蔽入口的编码绕过

位置
src/http/middleware.js:108（req.path === '/admin.html' 精确匹配）
状态
已复现：设置 ADMIN_ENTRY_KEY 后，GET /%61dmin.html 直接返回 200（绕过门禁）；裸访问仍 404

Express 的 req.path 不做百分号解码，而静态中间件会解码后再匹配文件—— 于是拼写变体（%61、混合大小写之外的编码变形等）全部绕过。修复： 对 path 先 decodeURIComponent 再比较（并 try/catch 非法编码）， 同时把「找到页面的 key」与「登录」的边界在文档里再说清一次——绕过门禁本身不等于拿到权限， 但会暴露后台入口与攻击面。

06工程质量亮点

这些部分经代码通读与实测验证，值得保留与继续发扬：

  • 服务端权威规则：王手过滤（含打子分支修复）、强制升变、千日手（含连续王手判负）、困毙、入玉宣言（AJSA 27 点法）都实现且有针对性注释，规则引擎的「候选走法必被 applyMove 接受」不变量思路正确。
  • 结构性安全机制：隐私字段出口白名单（stripPrivate）、唯一 checkAdmin 入口、adminWrite 统一审计包装、双生效点的 IP 封禁（HTTP + WS 握手）、限流分档——方向都对，问题只在个别实现漏口（见 P0/P1）。
  • 数据可靠性：备份用 VACUUM INTO（WAL 一致性快照）而非拷贝文件；对局快照 + 重启恢复实测有效（「已恢复 1 场未完成对局」，走法完整）；棋谱摘要列 + 索引避免全表解析。
  • 棋谱格式严谨：KIF/CSA 导出实测与 81Dojo 风格一致（含每手耗时、手合割标注、让子局上手/下手行序处理）。
  • 前端 XSS 防护总体到位：聊天用 textContent、评论/名称广泛走 esc；本次发现的单引号逃逸是一个系统性角度（写入路径与内联 onclick 的交叉），修复面很小。
  • 无 Cookie 架构：凭证全走 header/参数，CSRF 面天然关闭（注释里也写明「若改 Cookie 必须补 CSRF」——很清醒）。
  • 注释与设计文档化程度罕见：每个非常规决策都记录了为什么（含踩坑史），对维护者是巨大资产。
