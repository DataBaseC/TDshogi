# 存储关系化评估（2026-09-27）

> 结论：**仅完成评估，不做数据迁移**。当前业务数据以 JSON blob 存于单一 SQLite 的 kv 表，
> "一键一整块 JSON"带来写放大与全表解析；但关系化改造属高风险大改，方案建议**延后**，
> 本轮先用 §5.2/§5.4 压低只读路径压力（会话名缓存、分页）。

## 1. 现状：kv-blob 形态

- 落盘：单个 SQLite（`storage.js` 的 kv 表），键为逻辑路径（如 `sessions/<id>.json`、`ratings.json`、
  `accounts.json`、`announcements.json`…），值为**整块 JSON 文本**。
- 读取：`readJson(key)` 取整块 → `JSON.parse`；列表：`listJsonByPrefix(prefix)` 全量解析。
- 优点：零 schema、零迁移、极简；小规模下完全够用。
- 代价：
  - **写放大**：改一个字段要重写整块（如 `ratings.json` 改一个玩家积分 = 重写全表）；
  - **读放大**：列出/过滤要解析全部条目（排行榜、用户列表曾逐条落盘读）；
  - 无法用 SQL 做**部分索引/条件查询**，复杂查询只能"全量拉到内存再过滤"。

## 2. 关系化目标 schema（提议）

```sql
-- 会话（原 sessions/<id>.json）
CREATE TABLE sessions (
  id          TEXT PRIMARY KEY,        -- 24 hex
  name        TEXT NOT NULL,
  avatar      TEXT,
  created_at  INTEGER NOT NULL,
  last_seen   INTEGER,
  title       TEXT,
  banned_until INTEGER DEFAULT 0,      -- 0 = 未封禁
  net         TEXT,                    -- JSON（firstIp/lastIp/ua…），隐私，仅管理员出口
  secret      TEXT                     -- 游客持有证明（B1），绝不下发
);

-- 评级（原 ratings.json 的每个 key）
CREATE TABLE ratings (
  player_id   TEXT PRIMARY KEY,
  rating      INTEGER NOT NULL DEFAULT 1500,
  games       INTEGER NOT NULL DEFAULT 0,
  wins        INTEGER NOT NULL DEFAULT 0,
  losses      INTEGER NOT NULL DEFAULT 0,
  draws       INTEGER NOT NULL DEFAULT 0,
  points      INTEGER NOT NULL DEFAULT 0,
  exp         INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE rating_history (           -- 原 history 数组
  player_id   TEXT NOT NULL,
  t           INTEGER NOT NULL,
  rating      INTEGER NOT NULL,
  PRIMARY KEY (player_id, t)
);

-- 账号（原 accounts.json）
CREATE TABLE accounts (
  id            TEXT PRIMARY KEY,
  username      TEXT UNIQUE NOT NULL,
  salt          TEXT NOT NULL,
  pass_hash     TEXT NOT NULL,
  hash_alg      TEXT NOT NULL DEFAULT 'scrypt-v1',
  guest_id      TEXT,
  phone         TEXT,
  style         TEXT,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

-- 棋谱摘要（原摘要列已存在；关系化后可直接投影）
CREATE INDEX idx_ratings_rating ON ratings(rating DESC);
CREATE INDEX idx_sessions_lastseen ON sessions(last_seen DESC);
```

## 3. 迁移与回滚

**迁移（一次性，双写过渡）**
1. 建新表（`CREATE TABLE IF NOT EXISTS`）；
2. 读旧 blob → 拆行 upsert；
3. **双写期**：`readJson/writeJson` 包装层同时写 kv（旧）与新表（新），读以新表为准；
4. 观察一轮发布无异常后，停止写旧 kv，保留只读快照。

**校验**：迁移后逐键比对（`ratings.json` 行数 = 原对象键数；抽样字段相等）。

**回滚**：旧 kv 在双写期始终是最新（或至少可用），回滚即把读切回 kv；新表可保留不影响。

## 4. 建议

- 本轮**不迁移**：收益（查询能力）尚未成为瓶颈；风险（一次性大改 + 数据不可逆）显著高于收益。
- 先做**低风险替代**（本轮已做）：会话名进程内缓存（§5.2）、分页 limit/offset（§5.4）、KIF 缓存（§5.3）。
- 若后续确实需要复杂查询（如多条件检索棋谱、统计报表），再按上面的双写方案推进。
