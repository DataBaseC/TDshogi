# 依赖升级评估（2026-09-27）

> 结论：**本轮不升级 express（4 → 5）**。理由见下：破坏性变更逐条比对后，本项目**命中其中若干条**，
> 升级需要一次完整回归（且 e2e 覆盖的是 WS 主链路，REST 侧回归成本更高）。先把结论与清单留档，供后续排期。

## 1. 现状

| 依赖 | 当前范围 | 说明 |
|---|---|---|
| express | `^4.19.0` | REST + 静态资源 |
| ws | `^8.17.0` | WebSocket 主通道 |
| better-sqlite3 | `^13.0.3` | 同步 SQLite（业务存储） |
| shogi.js | `^5.4.0` | 将棋规则权威 |
| eslint | `^10.10.0`（dev） | |

Node 版本：`.nvmrc` = `22`（package.json `engines.node >= 22`；better-sqlite3 v13 需要 Node ≥ 22）。

## 2. express 5 的破坏性变更 vs 本项目命中情况

| # | express 5 变更 | 是否命中本项目 | 说明 / 影响面 |
|---|---|---|---|
| 1 | 路由通配符改用 path-to-regexp v8（`*` → `*splat`，需具名） | **命中** | 需全量排查 `app.get/post` 的 path 里是否有裸 `*`；本项目路由多为字面量路径，命中面小但需逐条核对。 |
| 2 | `req.query` 的解析器可选（默认仍用 qs，但可换 simple） | 否 | 未自定义 query parser。 |
| 3 | `res.send(status)` / `res.sendStatus` 行为微调 | 否 | 未使用该重载。 |
| 4 | 移除 `app.del`、`res.json(status,obj)` 等废弃 API | 否 | 未使用。 |
| 5 | `express.urlencoded` 的 `extended` 默认值 | 否 | 未使用 urlencoded（本项目只用 `express.json`）。 |
| 6 | 异步中间件里 rejected promise 会被透传（更好） | 获益 | 对 `handler` 里的 async 抛错更友好。 |
| 7 | `req.param()` 移除 | 否 | 未使用。 |

**命中项只有第 1 条**（若确有如 `/api/records/:id/*` 之类的通配路由则需改写；经检索当前未使用裸 `*` 通配，
但升级前仍应全量 grep 一遍以确认）。

## 3. 建议

1. **不在本轮升级**：当前 4.19 无已知在本项目暴露面的高危问题；升级收益（主要是维护性）不足以覆盖回归成本。
2. 若后续升级，按此顺序：
   - 单独开分支，先 `grep -rn "app\.\(get\|post\|put\|delete\|use\)(" src` 核对通配符；
   - 升 express 到 5，跑 `npm test` + 全量 e2e（`E2E_STARTUP_TIMEOUT_MS=180000 npm run e2e`）；
   - 重点观察：静态资源（`express.static`）、`/api/records/*` 系列、错误处理中间件的签名（express 5 要 4 参才当错误中间件）。
3. **ws / better-sqlite3 / shogi.js**：本轮的版本已满足需要，未见需跟进的破坏性变更。
