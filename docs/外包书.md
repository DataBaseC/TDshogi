## 一、项目概况

- **技术栈**：Node.js（CommonJS，无构建）+ vanilla JS 前端 + SQLite（better-sqlite3）+ npm 包 `shogi.js` 规则引擎。
- **运行**：`npm ci` → `node server.js`（默认 :3000，HTTP+WS 同端口）。`DATA_DIR` 环境变量指定数据目录。
- **测试**：`npm test`（node test runner，`tests/*.test.js`）。**当前基线 268 passing**，交付时全绿且含新增测试。打包校验 `npm run pack`。

### 分层架构（红线，甲方要求"修改时注意分层和架构"）

```
server.js                  HTTP/WS 装配（勿放业务逻辑）
src/http/                  REST 路由层（context.js 单例与身份解析；routes/*）
src/protocol.js            WS 协议层（消息分发、广播、REST 辅助出口）
src/rooms/                 房间域（lifecycle 建房/匹配、gameplay 对局、state、snapshot…）
src/game.js                棋规域（走法生成、合法性、升变、终局）★ Bug1
src/{records,storage}.js   棋谱域（业务 → SQLite 摘要列/索引）
src/{auth,accounts}.js     身份域（游客会话 / 账号+令牌+迁移）
src/ratings.js             评级/战绩/等级域
public/js/                 前端（只做展示交互，不得复制业务规则）
```

**必须遵守**（违反打回）：

1. `protocol` 只有 `src/http/context.js` 一个创建点，严禁别处 `new Protocol()`。
2. 身份解析只有 `resolvePlayer`（公开读、宽松）/ `resolveOwner`（归属判定、严格），管理鉴权用 `checkAdmin`，不得再抄一份。
3. 棋谱列表/检索走摘要列（`storage.listSummaries`），禁止全量解析整谱。
4. 对外数据出口过 `privacy.stripPrivate`。
5. **服务端权威**：升变合法性、匹配防自战等必须服务端校验，前端提示只是 UX。
6. `shogi.js` 的 `Shogi.move()` **不校验升变合法性**（给 promote 即无条件升变），不可依赖。

## 三、Bug 清单

### Bug 1｜棋驹从敌阵出来后没有提示可升变 【根因已确认，直接修】

**现象**：棋子从敌阵内移到敌阵外（出阵）时不弹升变提示。将棋规则：**移动起点或终点任一在敌阵内即有权升变**。

**根因**（代码审查确认）：`src/game.js` `candidateMovesFrom`（约 L424 起）只检查目标格：

```js
const canPromote = rawKind !== 'OU' && rawKind !== 'KI' && !Piece.isPromoted(piece.kind)
  && inPromotionZone(m.to.y, color);   // ← 只查 to.y，漏了 from.y
```

补上出发格：`inPromotionZone(m.to.y, color) || inPromotionZone(m.from.y, color)`（注意颜色参数，别写反先後手的阵）。

**必须一并修的安全缺口**：`isMoveLegal` / `applyMove`（`src/game.js`，约 L215 `promotionChoice`、L245 `applyMove`）把升变合法性交给 shogi.js，而它不校验。需补服务端校验：

- 无升变权（金/王/已升变，或 from、to 均在阵外）收到 `promote:true` → 拒绝（回 `move_invalid`）。
- 强制升变（步/香入敌阵末段、桂入最后两段）不升变 → 自动升变或拒绝，行为一致即可。

**测试用例（先写，应先红）**：

1. 银将 3三→3四（出阵）：候选着法含升变/不升变两选项。
2. 阵外→阵外：不含 promote。
3. 阵外→阵内：含 promote（防回归）。
4. 金/王/成银/成桂/成香/龙/马：永不出现 promote。
5. 步 2二（末段）请求不升变：被拒或自动升变（按选定方案断言）。
6. `isMoveLegal({promote:true})` 无权升变时返回非法。

**验收**：测试全绿；前端（`public/js/board.js`/`play.js` 升变确认 UI）出阵弹提示，手工走银将出阵确认。

### Bug 2｜加入房间后显示 ID 不正确 【服务端已排除，先复现锁定再修】

**现象**：加入房间后页面显示的房间 ID/房号与房主给出的房号对不上。

**已排除**（实证，模块层全对）：`rooms/lifecycle.js` `createRoom`/`joinRoom` 返回 `code` 正确；`getRoomStateForClient` 给 host/joiner 的 `state.code` 一致且正确；`src/rooms/snapshot.js` `_serializeRoom` 持久化/恢复均带 `code`。

**排查方向（按优先级）**：

1. 客户端显示：`public/js/play.js:144` `roomCodeLabel` ← `state.code`，确认 joiner 收到的 `code` 非空非旧值。
2. 跳转/绑定时序：`public/js/lobby.js:112-123` `room_joined`→`play.html?room=<roomId>`；`public/js/play.js:720-734` 进房三岔路（spectate / join=1 / `request_state {roomId}`）。**重点怀疑**：joiner 走了不带 roomId 的 `request_state {}` 时服务端回位到"当前绑定房间"——若残留旧房绑定就显示旧房号（本项目"幽灵房"历史问题同族，`src/rooms/lifecycle.js` 头部注释有背景）。

**测试用例**：e2e——A 建房→B 凭码加入→双方 `state.code` 与建房返回 `code` 三方一致；B 先进过别的房再加入新房→显示新房号（回归幽灵绑定）。

**验收**：e2e 全绿 + 手工双开浏览器"建房→分享房号→加入"显示一致。

### Bug 3｜改名/注册后个人页查不到棋谱；管理员管理用户显示"用户不存在" 【部分根因已确认】

**现象**：(a) 游客或注册账号改用户名后，个人页查不到棋谱；(b) 管理员管理该用户提示"用户不存在"。

**已排除**（实证，域/存储层全对）：改名前后 `records.listPlayerRecords(playerId)` 均能查到（`src/storage.js` `listSummaries` 按 `playerB/playerW` id 匹配，改名不影响）；注册迁移正确（棋谱/评级归账号 id，旧游客 id 查不到是预期）；`auth.adminRename` 同一 id 连续两次均成功。

**已确认缺陷（必修）——幽灵游客会话**：
`src/accounts.js` `migrateGuestData`（约 L282-316）把游客会话**复制**到账号 id（`auth.saveSession({...guestSession, id: accountId})`）但**从不删除** `sessions/<guestId>.json`。实证：注册后 `auth.getSessionRaw(旧游客id)` 仍在 → 同一人在 `auth.listSessions()`/管理员用户列表出现**两条**。这是管理端错乱的直接来源之一。
**修法**：迁移成功后删除（或标记 merged 并在 `listSessions` 过滤）旧游客会话；注意 `accounts.getAccount(guestId)` 防重复迁移守卫（L117）与审计日志不要破坏。

**待锁定**：

1. "用户不存在"唯一来源：`src/auth.js` `adminRename/banPlayer/unbanPlayer/adminSetTitle` → `getSessionRaw(playerId)` 为 null。`getSessionRaw`（约 L192）要求 `/^[0-9a-f]{24}$/`——**账号令牌（`<accountId>.<ts>.<sig>`）会被拒**。检查 `public/js/admin.js` 用户列表/详情/改名与 `src/http/routes/admin.js`（L46-77）在用户改名/注册后实际传的 id（会话 id？账号 id？令牌？名字反查？），找出错位的一环。
2. 个人页查不到棋谱：域层已排除，在协议/前端。核对 `public/js/profile.js` 身份链路（L33-36 `viewedId`/`myId`、L262 `loadProfile`→`/api/profile?player=`）与 `src/http/context.js resolvePlayer` 对令牌的解析在"改名/注册后重载"时序下是否取到旧值。
3. **顺手修**：`public/js/profile.js:386` `r.playerIds.b === guest.id`——账号用户 `guest.id` 是令牌而棋谱存账号 id，恒 false，胜/负着色全错。应用解析后的 `myId` 比对。

**测试用例（e2e）**：① 游客对局→改名→`/api/profile` 与 WS `record_search` 仍能查到；② 游客对局→注册→账号令牌能查到、旧 id 查不到；③ 用户改名后管理员 rename/ban/unban 均成功；④ 注册后 `listSessions` 该人只有一条。

**验收**：e2e 全绿；管理后台手工对改名用户改名/封禁/解封正常。

### Bug 4｜改名后或注册后会自己匹配到自己 【守卫已有，缺口在身份切换/残留清理】

**现象**：快速匹配匹配到自己（自己两个身份开局）。

**已排除**（实证）：`src/rooms/lifecycle.js` `quickMatch`（约 L219-275）已有双保险（入队同 playerId 拒绝 L246-251、配对同 playerId 不配 L261-265），同 playerId 双连接实测被拒。

**缺口（修复方向）**：守卫只认 `playerId` 相等。**注册后 playerId 变化**（游客 id→账号 id），旧连接/旧队列项带旧 playerId 留在 `matchQueue`，新连接以新 id 入队→两个不同 id 配对=同人自战。结合 Bug 3 的幽灵会话（注册后旧身份仍在），此状态确实可达。改名场景同理：改名/注册触发重载，旧 WS 残留在队列即双身份。

**修法（按层）**：

1. `src/rooms/lifecycle.js`：断线/换房/换身份时清理 `matchQueue` 残留（核对 disconnect 是否漏 `cancelMatch`）。
2. `src/protocol.js`/注册登录路径：**身份切换钩子**——升级账号时把旧 playerId 的队列项、房间绑定迁移或清除。
3. 安全网扩展：除 playerId 外，`accounts.listAccountsRaw()` 的 `guestId` 追溯（升级来源）也不得互配。**不要按 IP 拦**（误伤 NAT 后正常玩家）。

**测试用例**：① 同 playerId 双连接先后匹配：第二人被拒（守卫回归）；② 模拟注册前后双身份（旧 guest id+新 account id）先后入队→不成局（核心回归）；③ 入队后断线→队列无残留；④ 不同玩家正常配对（防过度拦截）。

**验收**：全绿；手工同浏览器注册前后各点一次快速匹配绝不成局。

### Bug 5｜棋驹声音没有播放 【实锤缺陷已定位，直接修 + 浏览器验证】

**现象**：落子/吃子音效不响。

**实锤缺陷**：`public/js/sound.js` `playFileSound`（约 L224-233）**违反自身契约**。注释称"文件缺失/格式不支持/自动播放被拦→返回 false 让调用方回退合成音"，实现却 `const p = a.play(); return true;`（无条件乐观返回，reject 被 `.catch(()=>{})` 吞掉）。调用方 `playMove()` = `if (playMoveFile(1)) return;`——进了 file 分支就**永不回退合成音**，文件 404/解码失败/自动播放被拦→**完全没声音**。
**修法**：回退做实——`a.play()` reject 或 `a.onerror` 时走合成音回退（fallback 回调或 async 返回）；注意部分浏览器 404 走 error 事件而非 play() reject。

**相关事实（已核对）**：

- `soundMove` 选项 `file:pieces/pieces_wood`（`public/js/settings.js` L57-59）→ `sound/pieces/pieces_wood.mp3`，**文件存在**（`public/sound/pieces/pieces_wood.mp3`）。
- `settings.js` SCHEMA 归一化会把非法值重置为 `default`，正常无脏值。
- 触发点：`public/js/play.js` 约 L557-565，`api.on('state')` 比较 `data.moves.length > lastMoveCount` 后 `playCapture()/playMove()`，逻辑本身正确；**请浏览器实测该回调确被执行**（若上方渲染 handler 抛错且 `api.js` 分发是整体 try/catch，声音连带被吞——顺手核对 handler 分发是否逐个隔离异常）。
- 自动播放策略：AudioContext 需用户手势激活（play.js 点击棋盘 `ensureCtx()`，已确认会 resume）；HTMLAudio 同受此限。

**测试用例**：`settings.js` 归一化（含 `file:pieces/pieces_wood` 保留）单测；`playFileSound` 失败路径回退合成音（注入 mock Audio）；浏览器手工：默认合成音、`棋子敲击` 文件音、文件改名后回退。

**验收**：浏览器三种设置均出声（或优雅回退），console 无报错。
