#### 13b 同身份双连接时请求被"静默丢弃" — ✅ **已完成（2026-09-23，与 13a 同一根因）**

- **症状**：同一 guestId 双连接后，先连的那条连接之后**既无回执也无 `error`**。
- **根因**：`protocol.js` 的 `clientId = ${session.id}_${Date.now().toString(36)}` ——
  后缀只有**毫秒时间戳**。同身份的两条连接在**同一毫秒**握手时 clientId **完全相同**，
  后到的连接覆盖 `clients` / `playerRegistry` 中原有的注册 ⇒ 先到的连接**收不到任何回执**
  （回执全发到后者的 socket 上）。实测碰撞率 **21/60 ≈ 1/3**，
  也解释了 `e2e-test.js`「同身份占用防护」段的历史抖动。
- **修复**：clientId 追加**进程内自增序号**（`this._connSeq`），保证唯一。
- ⚠️ 这不只是测试问题：**线上同一游客开两个标签页**若恰好同毫秒握手，其中一个会"失聪"。
- 遗留：该路径仍应在"同一身份新连接接管旧连接"时给旧连接一条明确消息（老约定「每条消息都要有出口」），
  目前只是不再碰撞；**要不要显式通知旧连接，留下一版**（低优先）。

  而实现也读旧表 ⇒ 两边"自洽"地全绿，真实数据在 kv、**一个都没清过**。
  已把测试改成 `auth.saveSession()` / `auth.listSessions()`（**测试的数据源必须与生产同一处**，
  这比"测试通过"重要得多）；改完这组用例才真正**保护**这个修复（旧实现下会挂）。
- **部署注意（重要）**：它是**唯一会真删数据**的模块，而线上"保留期"从未生效过 ⇒
  首次放开前**务必**先 `CLEANUP_DRY_RUN=1` 启动看一遍清单（会一次性清掉积压多年的过期游客与孤儿棋谱），
  并先 `npm run backup`。**因此 13c 不随 v1.4.6 上云，需按上述流程单独放行。**

#### 13d P0-4 完整方案：游客身份不能"id 即凭证"

v1.4.5 已让 6 个棋谱接口对**注册账号**强制令牌（新增 `resolveOwner()`），
但**游客仍是"知道 id 即身份"**。根治需引入**游客会话撤销 / 持有证明**机制 ——
这是"公开 id 当凭证"这个系统性弱点的最后一块（见 §Z8 教训 1）。

#### 13e 迁移凭据（P0-3 的完整方案）

v1.4.5 只做了最小修复（拒绝"已是注册账号的 id"作迁移来源）。
完整方案：游客会话里存一个**不下发**的 `migrationKey`，注册时携带它才允许迁移数据。

#### 13f P1-3 根治：管理页废弃字符串拼 `onclick` → `dataset` + 事件委托

`esc()` 已补转义单引号（v1.4.5 止血），但**拼 `onclick` 这个模式本身**还会再生同类死角。
根治 = 全面改 `dataset` + `addEventListener`。

#### 13f 的落地计划（本轮**未做**，避免 34 处盲改）

现状：`onclick="…"` 内联处理器共 **34 处** —— `admin.js` 19、`nav.js` 6、`review.js` 2、
`home/history/gallery/tournament/tournaments/profile/util` 各 1。
⚠️ **安全面已经止血**：`esc()` 从 v1.4.5 起会转义 `'`，原先那条"单引号逃逸 → 存储型 XSS"已关闭。
所以剩下的是**卫生问题**（字符串拼 HTML 的属性，今后每加一个字段都要重新审一遍转义）。
做法（一次只改一个文件，改完跑 `npm run e2e` + 手动点一遍该页）：
1. 把 `onclick="fn('${id}')"` 换成 `data-act="ban" data-id="${esc(id)}"`；
2. 在容器上挂一次 `addEventListener('click', …)` + `e.target.closest('[data-act]')` 分派；
3. 值里的引号从此与 HTML 无关（仍要 `esc` 防 HTML 注入）；
4. 建议先做 `admin.js`（19 处、风险最集中），它做完再顺手清其它 15 处。

#### 13d / 13e 的设计草案（两条同源，建议一起做）

**共同问题**：`resolveOwner()` 只解决了"**注册账号**必须凭令牌"，而**游客**仍是"知道 id 即身份"。
要根治，得让游客也持有一样**只有他浏览器知道、且不下发**的东西。

- **13d 游客持有证明**：在**游客会话**里生成 `secret`（32 字节 hex，写在 `sessions/<id>.json`，
  **绝不出现在任何下发字段里**——`publicInfo`/`playerCard`/`profile` 都要拦住，参照 `stripPrivate` 的做法）。
  前端把它存在 `localStorage`（与 `guest.id` 一起），所有"以游客身份读写自己资源"的请求
  都带上 `guest=<id>&key=<secret>`；服务端 `resolveOwner()` 增加校验：
  **游客 id 必须同时带对 key** 才认，否则返回 null（等价于未登录）。
  ⚠️ **兼容期**：老浏览器没有 key ⇒ 直接拒绝会让现有游客"丢身份"。
  建议两步走：先只对**写操作**强制（读先放行并记日志统计比例），一个版本后再对读强制。
- **13e 迁移凭据**：同一把 `secret` 顺带解决 —— `register` 时要求带上 `migrationKey`
  （= 游客会话里的 `secret`），**只有持有者**才能把该 id 的数据迁到自己账号。
  v1.4.5 的最小修复（拒绝"已是注册账号的 id"）保留为兜底。
- 影响面：`src/auth.js`（生成/校验）、`src/http/context.js`（`resolveOwner`）、
  `src/protocol.js`（`register` 的 guestId 校验、`hello` 下发策略）、
  前端 `public/js/api.js` / `profile.js` / `history.js`（带 key）。
- 验收：新增 e2e —— ① 不带 key 的游客 id 写操作必须 403；② 带对 key 的正常可用；
  ③ 迁移必须携带 key（拿别人 id 迁移失败）。
