# 赛事系统 2.0 设计文档

> 2026-09-13 用户提出需求 8–12，本文是完整设计。
> 现状实现见 `src/tournaments.js`（283 行，轻量单败淘汰：建赛 → 管理员审核 → 满员自动开赛 → 晋级 → 冠军）。
> **本次是重构级扩展**，不是加几个字段——权限体系、报名流程、赛后存档都是新的。
>
> 需求原文（用户口述，本文按此设计）：
> 8. 赛事页（每个赛事唯一 id）+ 我的赛事按钮 + 赛事列表 + 赛事管理页（主办人和管理员权限不同）
> 9. 申请建赛需填表：报名起止时间、比赛起止时间、举办理由、赛制（当前仅单败淘汰，其余待实装）；管理员审核后才能开始
> 10. 主办人可管理自己创办的**未结束**赛事：设冠军、审重赛、踢人、安排轮次、取消赛事、取消选手成绩、通过报名
>     ⚠️ 其中「**设冠军**」经用户 2026-09-13 修正为**仅管理员**（见 §1 权限矩阵、§7/§8）；
>     此处保留需求原文以存证，**实现时不要按这句写**
> 11. 管理员有全部权限；**比赛结束后主办人无权操作**，结果存档，**只有管理员可编辑**
> 12. 赛事详情页所有用户可查看赛事棋谱；**赛事棋谱默认（强制）公开**；参赛选手可申请重赛

## 0. 关键决策速览

| # | 决策 | 理由 |
|---|---|---|
| D1 | 新增 `registration` / `archived` 两个状态 | 现有 `open` 只表示"可报名"，但要区分"报名期是否已开始/结束"；`archived` 承载需求 11 的"结束后只读+仅管理员可编辑" |
| D2 | **权限判定收敛到单一函数** `canManage(t, actor)` | 与 §M2 管理鉴权同源教训：两处各写一遍判定，迟早出现"某条路径漏判"。所有管理写操作先过它 |
| D3 | 报名**两段式**：`entrants[]`（报名池）→ `players[]`（开赛时冻结） | 需求 10 要"通过/踢出报名"，而现有 `players` 直接就是参赛者，混在一起无法回滚 |
| D4 | 赛事棋谱**强制公开**（用户已确认） | 在落盘环节写死 `visibility='public'`，不给"忘记设"的机会 |
| D5 | 赛后**不是删除权限而是转移**：`archived` 后主办人只读、管理员可编辑，且**每次编辑留痕**（`adminEditLog`） | 需求 11 要求"只有管理员可编辑"，但编辑必须可追溯——否则管理员改成绩无从查证 |
| D6 | 状态变更**全部走一个 `mutate()` 包装**，自动写 `logs[]` | 需求 10/11 涉及大量管理动作，操作日志是事后追责与排障的唯一依据 |

## 1. 角色与权限矩阵

**四种角色**（同一个人在不同赛事里角色可能不同）：

| 角色 | 判定 |
|---|---|
| **管理员** | `admin.verify(token)` 通过（§Q7-5 统一入口） |
| **主办人** | `t.ownerId === actor.id` |
| **参赛选手** | `t.entrants` 中 `status === 'approved'`（或 `players` 内） |
| **访客** | 其余（含未登录） |

**权限矩阵**（✅ 可 / ⛔ 不可 / 📖 只读）：

| 操作 | 管理员 | 主办人（未存档） | 主办人（已存档） | 选手 | 访客 |
|---|---|---|---|---|---|
| 建赛申请 | ✅ | ✅ | — | ✅（需登录正式账号） | ⛔ |
| 审核建赛（通过/拒绝） | ✅ | ⛔ | ⛔ | ⛔ | ⛔ |
| 报名 | ✅ | ✅ | — | ✅ | ⛔ |
| 批准 / 拒绝报名 | ✅ | ✅ | ⛔ | ⛔ | ⛔ |
| 踢出选手 | ✅ | ✅ | ⛔ | ⛔ | ⛔ |
| 取消选手成绩 | ✅ | ✅ | ⛔ | ⛔ | ⛔ |
| 安排轮次（手动建房） | ✅ | ✅ | ⛔ | ⛔ | ⛔ |
| 设置冠军 | ✅（**唯一**，主办人亦不可） | ⛔ | ⛔ | ⛔ | ⛔ |
| 撤销/更改已设冠军 | ✅（唯一） | ⛔ | ⛔ | ⛔ | ⛔ |
| 审核重赛申请 | ✅ | ✅ | ⛔ | ⛔ | ⛔ |
| 申请重赛 | ⛔ | ⛔ | ⛔ | ✅ | ⛔ |
| 取消赛事 | ✅ | ✅（**仅未结束时**） | ⛔ | ⛔ | ⛔ |
| **存档后编辑**（改冠军/改成绩/改备注） | ✅（留痕） | ⛔ | ⛔ | ⛔ | ⛔ |
| 查看详情 / 棋谱 | ✅ | ✅ | ✅ | ✅ | ✅ |

**实现要求**：上表**只允许存在于一处**——`tournaments.js` 导出的 `canManage(t, actor, action)`。
路由层（`src/http/routes/tournaments.js`）与 WS 层都调它，**不再各写 `if (t.ownerId === me)`**。

## 2. 数据模型

在现有 `tournaments.json`（`{ <id>: tournament }`）基础上扩展：

```js
{
  // ---------- 基本 ----------
  id: 'a1b2c3d4',                 // 8 位短 id（唯一，需求 8 的"唯一 id"）
  name: '暑期棋王赛',
  size: 8,                        // 4~32 且为 2 的幂（需求 Q3 已确认扩充）
  format: 'single-elimination',   // 赛制；预留 'swiss' | 'round-robin'（需求 9：其余待实装）
  ownerId: '<24hex>',
  ownerName: '张三',               // 冗余存快照（账号可能被删）
  createdAt: Date.now(),

  // ---------- 建赛申请（需求 9）----------
  reason: '面向新手的周末赛',        // 举办理由
  registerStart: ts, registerEnd: ts,   // 报名起止
  matchStart:   ts, matchEnd:   ts,     // 比赛起止
  requireApproval: true,          // 报名是否需主办人批准（默认 true）

  // ---------- 审核 ----------
  status: 'pending_approval',     // 见 §3 状态机
  reviewedAt: null, reviewedBy: null,
  rejectReason: '',               // 拒绝/取消的原因（复用现有 reason 字段语义，见 §3 迁移说明）

  // ---------- 报名池（新增，D3）----------
  entrants: [
    { id, name, at, status }
    // status: 'pending' | 'approved' | 'rejected' | 'kicked' | 'withdrawn'
  ],
  players: [],                    // 开赛时由 entrants 中 approved 冻结而来

  // ---------- 对阵（沿用现有）----------
  bracket: [],                    // 平铺满二叉树，见 makeBracket
  championId: null,
  championManual: false,          // 是否为主办人/管理员手动指定（需求 10）

  // ---------- 重赛（需求 10/12）----------
  rematches: [
    { id, matchId, nodeIndex, byId, byName, reason, at,
      status: 'pending' | 'approved' | 'rejected',
      decidedBy: null, decidedAt: null, note: '' }
  ],

  // ---------- 操作日志（D6）----------
  logs: [
    { at, byId, byName, byRole: 'admin'|'owner', action, detail }
  ],

  // ---------- 赛后存档（需求 11）----------
  endedAt: null,
  archivedAt: null,
  adminEditLog: [ { at, byId, field, from, to, note } ],

  // ---------- 对局关联（需求 12）----------
  matchIds: []                    // 本赛事产生的所有房间 id（含已结束），用于聚合棋谱
}
```

**向后兼容**：旧数据没有 `entrants` / `logs` 等字段 → `publicInfo()` 一律用 `|| []` 兜底（现有代码已有此风格，如 `reviewedAt || null`）。`status: 'open'` 迁移为 `'registration'`（读时映射，见 §3）。

## 3. 状态机

```
                    ┌──────────────────────────────┐
                    │  pending_approval            │  ← 建赛申请提交
                    │  （待管理员审核）              │
                    └──────────┬───────────────────┘
              approve          │            reject
        ┌──────────────────────┴──────────────────────┐
        ▼                                             ▼
┌────────────────┐                              ┌──────────┐
│ registration   │  报名期（registerStart ~ end） │ rejected │
│ 报名中/待开赛   │                              └──────────┘
└───────┬────────┘
        │  开赛（满员自动 / 主办人手动 / 报名截止）
        ▼
┌────────────────┐
│ playing        │  比赛中（对阵推进）
└───────┬────────┘
        │  决赛出结果 / 管理员设冠军
        ▼
┌────────────────┐
│ finished       │  已结束（主办人仍有权限，用于收尾）
└───────┬────────┘
        │  自动（决赛后 N 小时）或管理员手动
        ▼
┌────────────────┐
│ archived       │  已存档：主办人只读、管理员可编辑（留痕）
└────────────────┘
```

**侧分支**：`registration` / `playing` / `finished` 均可 → `cancelled`（管理员或主办人，需求 10）。
**注意**：`cancelled` 与 `archived` 不同——前者是"没办成"，后者是"办完了、封存"。

**迁移**：旧的 `status: 'open'` 在读取时映射为 `'registration'`（`publicInfo` 里做一次映射，不改磁盘数据）；
写回时统一用新值。`t.reason` 在旧数据里表示"拒绝/取消原因"，新模型拆成 `rejectReason`（审核）与
`rematch.reason` 等，读取时若 `rejectReason` 为空则回落到 `reason`。

## 5. 建赛申请（需求 9）

**表单字段**（全部必填，除标注）：

| 字段 | 校验 |
|---|---|
| 赛事名称 | 1–20 字符（沿用现有） |
| 人数 | 4/8/16/32（2 的幂，Q3 已确认） |
| 赛制 | 下拉，当前仅「单败淘汰」（其余项 disabled 标注"待实装"） |
| 举办理由 | 10–200 字符 |
| 报名开始 / 结束 | 时间戳；`start < end`，且 `end > now` |
| 比赛开始 / 结束 | 时间戳；`matchStart >= registerEnd`，`matchEnd > matchStart` |
| 报名是否需审核 | 开关，默认**开**（Q2 已确认） |

**服务端校验**（不信任前端，`src/tournaments.js` 的 `createTournament`）：
时间顺序、人数档位、理由长度全部在服务端再验一遍；失败返回具体原因（如"报名结束时间早于开始时间"）。

**流程**：提交 → `pending_approval` → 管理员在「赛事管理」审核（现有 UI 已有 approve/reject）→
通过后进入 `registration`，**按 `registerStart` 自动开放报名**（未到时间则显示倒数）。

## 6. 报名（需求 8 / Q2 已确认"两者都要，可配置"）

| `requireApproval` | 行为 |
|---|---|
| `true`（默认） | 报名进入 `entrants[].status = 'pending'`，**待主办人批准**；批准后变 `approved` |
| `false` | 报名即 `approved` |

**共同规则**：
- 只有**正式账号**可报名（游客不可——否则 30 天清理会把参赛者清掉，见 §9），沿用现有"建赛需登录"的约束；
- 名额按 `size` 计，`approved` 数量达到 `size` 时**自动开赛**（沿用现有逻辑），或由主办人手动开赛；
- 报名截止（`registerEnd`）后自动停收；未满员则**按实际人数开赛**，首轮**轮空**（`size` 与实到人数不等时，
  用 `null` 占位叶节点，`assignNextMatches` 里把"对手为 null"的场次直接判晋级）。

⚠️ **轮空的实现要点**：现有 `assignNextMatches` 要求两个子节点都有 `readyPlayer` 才建房；
新增 `null` 分支——若仅一方有值，直接把该方 `winnerId` 填到父节点（等于轮空晋级），并写 `logs`。

## 7. 主办人管理操作（需求 10）

全部**仅在 `registration` / `playing` / `finished` 且未存档**时可用（`canManage` 判定）：

| 操作 | 说明 | 注意 |
|---|---|---|
| 通过 / 拒绝报名 | `entrants[].status` 变更 | 拒绝可附理由 |
| 踢出选手 | `status = 'kicked'`；若已在 `players` 则从对阵中移除 | 若该选手已有进行中比赛 → 需先解散，或视为"取消成绩" |
| 取消选手成绩 | 该选手所有已赛对局判负，对手晋级 | **必须记 `logs`**；波及的比赛需重算对阵 |
| 安排轮次 | 手动触发 `assignNextMatches`（补建房） | 用于自动分配失败时的兜底 |
| 审核重赛申请 | `rematches[].status` = approved / rejected | 批准后**作废该场结果**并重建该节点对局 |
| 取消赛事 | 转 `cancelled`，返回 `matchIds` 供 rooms 解散 | 沿用现有 `cancelTournament`；**仅未结束时**（见下） |

> ⚠️ **「设置冠军」不在主办人权限内**（2026-09-13 用户明确："**只有管理员可以手动设冠军**"）。
> 需求 10 原文含"主办人可以设置冠军"，**已被用户修正** → 该操作只出现在 §8 的管理员权限中。
>
> ⚠️ **取消赛事的边界**（2026-09-13 用户明确："**主办人结束后不能取消赛事**"）：
> 主办人仅可取消 `registration` / `playing` 状态的赛事；进入 `finished` 后**不可取消**
> （此时只能走"存档"，且仅管理员可编辑）。

**严禁**：主办人对**别人的**赛事做任何操作；对**已存档**赛事做任何操作（需求 11）。

## 8. 管理员权限与赛后存档（需求 11）

- 管理员拥有 §7 的**全部操作**，且对象是**任意赛事**；
- **「设置冠军」是管理员专属操作**（2026-09-13 用户明确："只有管理员可以手动设冠军"）：
  `championId` + `championManual = true`，状态转 `finished`；用于提前结束（并列 / 弃权 / 赛程无法继续）。
  **管理员也可撤销已设冠军并恢复比赛**——保留这条是为了留出纠错能力（设错了能改），
  但每次变更都写 `logs`，可追溯；
- **取消赛事**：管理员对任意未结束赛事可用；**对 `finished` / `archived` 不可取消**（与 §7 的主办人限制一致）；
- 赛事进入 `archived` 后：
  - 主办人 → **只读**（UI 上隐藏全部管理按钮，服务端也拒绝）；
  - 管理员 → **仍可编辑**（改冠军、改成绩、改备注），但**每次编辑写入 `adminEditLog`**
    （`{ at, byId, field, from, to, note }`），详情页对管理员可见"编辑历史"；
- **存档时机**：决赛出结果后 `N` 小时自动存档（`N` 默认 24，可配），或管理员手动存档
  （给主办人留一个"赛后收尾窗口"，避免比赛刚完就无法处理申诉）。

## 9. 赛事棋谱（需求 12 / Q4 已确认"强制公开"）

- 赛事对局由 `matchFactory(tournamentId, players)` 建房 → 房间携带 `tournamentId`；
- **棋谱落盘时强制 `visibility = 'public'`**（在 `src/rooms.js` 的落盘路径里判断 `room.tournamentId`，
  而不是靠调用方记得传参——这是 D4 的落地方式）；
- 棋谱记录新增 `tournamentId` 字段 → 详情页据此聚合"本赛事全部棋谱"；
- **选手申请重赛**：仅该场比赛的两名选手可发起，写入 `t.rematches`，等主办人/管理员裁决。

#### T8 实施记录（2026-09-15）——已完成的部分

**已完成**：`src/swiss.js`（纯函数）+ `tests/swiss.test.js`（**12 项**）

做成**纯函数**是刻意的：瑞士制的正确性全在配对算法里（不重复对阵、奇数轮空、
配不出来时怎么退让、同分排序的确定性），而这些与"房间怎么建、状态怎么存、前端怎么画"
完全无关。剥出来后就能用单测把边界钉死，不必为了验证配对待造一整套赛事。

| 函数 | 作用 |
|---|---|
| `computeStandings(players, rounds)` | 汇总积分（胜 1 / 和 0.5 / 负 0 / **轮空视同胜得 1**）+ 对手列表 + 对手分 SOS |
| `rankStandings(entries)` | 名次：积分 ↓ → 对手分 ↓ → **参赛序兜底** |
| `pairRound({ standings, allowBye })` | 生成下一轮配对（相邻配 + 不重复 + 奇数轮空 + 退让） |
| `suggestRounds(n)` | 建议轮数 `max(3, ceil(log2(n)))` |

**两个关键设计**：
1. **排序必须确定性**：`pairRound` 建立在名次之上，而 `Array.sort` 在比较函数返回 0 时
   不保证稳定顺序（Node 虽稳定，但依赖它等于把正确性押在实现细节上）。
   所以最后一定用"参赛顺序"兜底——否则同样数据两次算出不同对阵，测试会随机失败、线上会莫名换对手；
2. **配不出合法组合时逐级退让，绝不抛错**：先允许重复对阵（2 人赛的唯一解就是重复），
   再放弃；返回值里用 `degraded` 标注，让主办人知道"这轮不完美"。
   宁可这轮有瑕疵，也不能让整个赛事卡在"配不出对"上。

**接线与前端（同日晚些时候完成）**：

| 项 | 实现 |
|---|---|
| 数据模型 | `format: 'swiss'` + `totalRounds` + `rounds: [{ round, pairs, byes, results, matchIds, matchPairs, degraded }]` + `currentRound`。⚠️ **不复用 `bracket`**——瑞士制没有淘汰树，`bracket` 恒为空数组 |
| `createTournament` | `FORMATS` 加 `'swiss'`；轮数不填则 `suggestRounds(size)`；限制 **3~9 轮** |
| `startTournament` | 按赛制分支：瑞士制 → `startSwissRound(t, 1)`；淘汰赛 → 原 `makeBracket` + `assignNextMatches` |
| `onMatchFinished` | 赛制分支 → `swissOnMatchFinished`：记赛果 → `swissRoundDone` 才推进 → 轮数跑完 `finishSwiss` |
| `publicInfo` | 下发 `formatLabel` / `totalRounds` / `currentRound` / `rounds` / `standings` / `championTie`；**只给瑞士制算 standings**（列表页会批量调 publicInfo） |
| 前端 | 建赛表单启用瑞士制 + 轮数下拉 + 说明；详情页 `renderSwissCard`（**轮次列表 + 名次表**）；列表页 `metaLine()` 显示"第 N/M 轮"；admin 列表显示赛制与轮次 |
| 循环赛 | 需求原文未要求，暂不做（瑞士制已覆盖"多轮比积分"的诉求） |

**实施中修掉的 3 个坑**：

1. ⚠️ **取消赛事不会解散瑞士制的房间**：`cancelTournament` 只从 `bracket` 收房间 id，
   而瑞士制的房间在各轮的 `matchIds` 里 → 返回**空数组**，赛事显示"已取消"、
   参赛者却还在房里下棋。抽出 `liveMatchIds(t)` 按赛制分路（**已加测试盯住**）；
2. ⚠️ **赛后定位不到"这一场是谁打谁"**：`matchIds` 在每场打完后会被清空（防重复回调），
   于是重赛申请找不到场次。新增 `rec.matchPairs`（matchId → 双方）留档；
3. ⚠️ **重赛在瑞士制下的语义**：没有"上游"可清，且改历史轮次的成绩会让**已经开打的后续轮次**
   失去配对依据。处理方式：**只允许对当前轮申请**，非当前轮在申请与裁决两处都拒绝——
   与其做一个半吊子的"改历史"，不如把规则收紧（冠军按名次算，撤回冠军比拒绝重赛伤害更大）。
